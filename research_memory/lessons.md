## LESSON-001

Observation:
strategy/survivor.py's PE and CE entry triggers are `if` / `elif`, not two
independent `if` statements (see lines ~378 and ~409). PE is checked first.
On any tick where PE's price-gap condition is met -- even if the trade is
then internally skipped for another reason (VIX-based qty=0, capital
limit) and NO PE trade is ever recorded -- the `elif` for CE is never
evaluated on that tick. This silently shifts which tick CE eventually
fires on, changing its entry price and P&L, independent of whether PE
ever actually traded.

Evidence:
Confirmed via two backtest-gate runs on survivor.pe_enabled True vs False
(candidate bed3749a), both producing the SAME CE trade count with
DIFFERENT P&L, on windows where zero PE trades occurred in either run
(research_archive.db backtest_runs run_ids BT_SURV_1d57c4cdf8 /
BT_SURV_ddb1efe82b). The engine itself is deterministic for a fixed
config (see BT_SURV_503c911d47 / BT_SURV_03c8b2b950, same window run
twice with unchanged config, byte-identical P&L -250.53) -- so this is a
real strategy-logic coupling, not backtest noise. This means candidate
bed3749a cannot be validly gate-tested until this is resolved; any
pe_enabled A/B result is confounded by tick-priority, not a clean
measurement of PE's own effect.

Confidence:
HIGH (code-level finding, directly verified against strategy/survivor.py
and two independent backtest-gate result pairs)

Status:
Open -- design question, not resolved. Not touched without explicit human
sign-off: was PE-before-CE priority intentional (e.g. deliberately
favouring PE, or deliberately allowing only one side to fire per tick), or
should the two checks be independent `if` statements?

(source: manual code review during candidate bed3749a gate-testing,
2026-08-29 -- not raised via the automated hypothesis pipeline)

STRONG UPDATE (2026-08-29, later same day): the user provided the ORIGINAL
reference implementation of this strategy (original_strategies/survivor_original.py,

In the original design, PE and CE were two fully INDEPENDENT method calls,
both run unconditionally every tick:
    self._handle_pe_trade(current_price)
    self._handle_ce_trade(current_price)
No elif, no priority, no coupling between the two sides at all.

The current strategy/survivor.py combines both into a single
if pe_enabled and <PE conditions>: ... elif ce_enabled and <CE conditions>: ...
block -- this coupling was introduced during the port to the current
architecture, not part of the original design. Given the original author
never intended one side to block the other, this looks like an
unintentional regression rather than a deliberate choice.

Revised status: this is now a probable BUG, not a genuine open design
question -- but it is still LIVE STRATEGY CODE and has NOT been changed.
Any fix requires explicit human sign-off and careful paper-mode testing
before going anywhere near live capital, same safety boundary as always.

SEPARATE FINDING from the same comparison: the current strategy also adds
a full daily re-anchoring step (reset_daily_strategy_state(), re-anchors
PE/CE reference points to the morning open price every day) that does not
exist anywhere in the original. This is a second, independent behavioral
difference worth investigating on its own -- not necessarily wrong, but a
real design change from the original that has not been evaluated for its
own effect on the losing streak.
